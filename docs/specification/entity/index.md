# Entity

An entity may be defined as a thing that is capable of an independent existence that can be uniquely [identified](#identifiers), and is
capable of storing data.

## Entity Name

All entity names are strings that must be unique in the system. It is possible to choose an `alias` to replace the unique entity name when
generating API paths (if the API designer wishes to override the unique name).

> All entities schemas are expected to be stored in the path `entities/{entityName}.yaml`, relative to the root service specification yaml.
> file.

## Identifiers

All entities in the system have a unique identifier. The `id` property is automatically included on all entities. Schemas that have the `id`
property auto-assigned use [System Identifiers](#system-identifiers).

Schema designers may choose to specify their own schemas for unique identifiers, if the identifier makes sense in the business domain, we
call these [Natural Identifiers](#natural-identifiers). For example, all vehicles have a unique
[VIN](https://en.wikipedia.org/wiki/Vehicle_identification_number), as such in a system where vehicles are part of the domain it may make
sense for the VIN to be the unique identifier for vehicles.

### System Identifiers

All system identifiers are [UUIDs](https://en.wikipedia.org/wiki/Universally_unique_identifier).

We chose UUIDs as they are universally unique identifiers. They are simply to generate and do not collide with other UUIDs, as such, it is
easy to migrate data from one environment to another without having the re-map identifiers.

**Example**

The following is an example of how to specify a system identifier:

```yaml
type: object
properties:
  # other properties
```

The following is an example of a system generated identifier:

```
f3f2e850-b5d4-11ef-ac7e-96584d5248b2
```

### Natural Identifiers

Natural identifiers are identifiers that have context outside the system. They are generally industry standard values that ensure their own
global uniqueness. Moreover, it makes sense to leverage the contextual identifier within the system as well.

Again, an example are vehicles that have a unique [VIN](https://en.wikipedia.org/wiki/Vehicle_identification_number).

**Example**

The following is an example of how to specify a natural identifier:

```yaml
type: object
properties:
  id:
    type: string
    pattern: [0-9A-Z]{17}
    example: 1HGBH41JXMN109186
  # other properties
```

## Entity Schema

The entity schema is derived as a subset of [JSON Schema](https://json-schema.org/).

We do not support the advanced features such as `allOf`, `anyOf`, `oneOf`, `if`, `then`, `else` which create conditional schemas as these
make code generation extremely complex and solutions usually exist that do not require such complexity.

### Schema Extensions

We have extended JSON schema to include additional keywords for the root level [entity](#entity-keywords) as well as
[property](#property-keywords) level keywords.

#### Resource Ownership

All entities in the system have a base ownership structure. They are either [globally owned](#global) (accessible by all users in all
tenants), [tenant owned](#tenant) (accessible by all users in a given tenant), or [user owned](#user) (accessible by a specific user in a
given tenant).

The ownership is not included in any **API paths** generated by the system, they are implicit. The users authentication token (JWT) defines
who the user and tenant are (or who the impersonated user and impersonated tenant are).

##### Global

The entity is owned by the system.

All operations that work on a global entity do not need to be restricted implicitly.

##### Tenant

The entity is owned by the tenant.

All operations that work on a tenant entity be restricted implicitly by the current `tenantId` (i.e. include a tenantId = {tenantId} in the
`WHERE` clause)

##### User

The entity is owned by the user.

All operations that work on a user entity be restricted implicitly by the current `userId` (i.e. include a tenantId = {tenantId} AND userId
= {userId} in the `WHERE` clause)

#### Entity Keywords

| Keyword                   | Description                                                             | Schema                                 | Default  |
| ------------------------- | ----------------------------------------------------------------------- | -------------------------------------- | -------- |
| ownership                 | The subject that [owns](#resource-ownership) the resource               | `enum: [ "global", "tenant", "user" ]` | `global` |
| singleton                 | Flags the entity as a singleton under the resource owner                | `boolean`                              | `false`  |
| <a href="alias">alias</a> | Replaces the entity name in all OpenAPI terms (path, params, etc)       | `string`                               |          |
| versioned                 | Flags the entity as versioned (stores revision history)                 | `boolean`                              | `false`  |
| readOnly                  | Flags the entity as readOnly in the API                                 | `boolean`                              | `false`  |
| createable                | Flags the entity as createable in the API (can be created)              | `boolean`                              | `true`   |
| editable                  | Flags the entity as editable in the API (can be updated after create)   | `boolean`                              | `true`   |
| deleteable                | Flags the entity as deleteable in the API (can be deleted after create) | `boolean`                              | `true`   |

#### Property Keywords

| Keyword             | Description                            | Schema                           |
| ------------------- | -------------------------------------- | -------------------------------- |
| readOnly            | Flags the field as readOnly in the API | `boolean`                        |
| data-classification | Defines the data classification        | `enum: [ "public", "sensitive ]` |

## Relationships

A relationship captures how entities are related to one another. Relationships can be thought of as verbs, linking two or more nouns.
Examples include an owns relationship between a company and a computer, a supervises relationship between an employee and a department, a
performs relationship between an artist and a song, and a proves relationship between a mathematician and a conjecture.

Every relationship has a `left` (or source) entity and a `right` ( or destination) entity. The `left` entity is always the entity where the
relationship was defined (i.e. the entity schema where the relationship was established).

Relationships are always treated as bidirectional, as such the system also creates an `inverse` relationship.

### Relationship Name

Every relationship has a name. The name must be unique within the scope of the `left` entity, it does NOT need to be globally unique.

### Defining relationships

There are two ways to specify relationships: through `rel` properties or through `links`. Both create the same types of relationships;
however, they affect the generated entity schemas in different way.s

#### `rel` property

A `rel` property both defines a relationship AND embeds the related entity's `id` property inside the entity.

The `rel` property is primarily used when the API designer wants the API client to specify the related entity instances when mutating the
source entity. For example, a user is placing an `order` the includes multiple `product` identifiers.

This works well with [association](#association) relationships.

The [cardinality](#relationship-cardinality) is determined based on whether the `rel` property is embedded inside an array's items or not.
If the `rel` property is in an array, then the cardinality is defaulted to `*..*`, otherwise it defaults to `*..1`

With a `rel` property, the [relationship name](#relationship-name) is automatically determined based on the property name.

**Example**

The following entity specification...

```yaml
type: object
properties:
  widgets:
    type: array
    items:
      rel: widget
  # other properties
```

...would produce the following **OpenAPI** schema definition...

```yaml
type: object
properties:
  widgets:
    type: array
    items:
      $ref: "#/components/schemas/WidgetIdentifier"
  # other properties
```

...and would be assigned the [relationship name](#relationship-name) `widgets` and have [cardinality](#relationship-cardinality) `*..*`.

#### `link`

A `link` defines a relationship between two entities and DOES NOT modify the entity properties in any way. It is expected that the
relationship is established through some other method, i.e. not through a direct mutation of the entity. For example, the relationship could
be established through an offline ETL process or similar manner.

With a `link` property, the [relationship name](#relationship-name) is automatically determined based on the property name.

**Example**

```yaml
type: object
properties:
  # other properties
links:
  widgets:
    rel: composition
    cardinality: 1..*
```

### Relationship Types

There are three main types of relationships in the service specification [association](#association), [composition](#composition), and
[aggregation](#aggregation).

#### Association

`Association` implies a general relationship where two entities. Neither entity is the `parent` nor `child` of the other entity, there is
simply some link between the two.

> All relationships a `association` by default.

#### Composition

`Composition` implies a parent-child relationship where the child cannot exist independent of the parent. Example: House (parent) and Room
(child). Rooms don't exist separate to a House.

> `Composition` is the main relationship type used to establish `parent-child` relationships in the system. These impact how
> [collections](../collections.md) are established.

#### Aggregation

`Aggregation` implies a parent-child relationship where the child can exist independently of the parent. Example: Class (parent) and Student
(child). Delete the Class and the Students still exist.

> NOTE - Aggregation was included for completeness from UML concepts; however, currently all [aggregation](#aggregation) relationships are
> treated as [associations](#association).

### Relationship Cardinality

Cardinality defines how many instances of one entity are related to instances of another entity, usually represented in terms of `X..Y`,
where `X` is the number of instances of the left or source entity, and `Y` is the number of instances of the right or destination entity.
`X` and `Y` are normally either `one` or `many`, represented as `1` and `*` respectively in the specification.

| Cardinality  | Specification | Inverse |
| ------------ | ------------- | ------- |
| One-to-one   | `1..1`        | `1..1`  |
| One-to-many  | `1..*`        | `*..1`  |
| Many-to-one  | `*..1`        | `1..*`  |
| Many-to-many | `*..*`        | `*..*`  |

> Both `1..1` and `*..1` imply that the destination entity is a singleton inside the parent collection, resulting in an `Upsert` rather than
> `Create`, `Update`, `Delete` style mutation.

> The cardinality of the `inverse` relationships is always inverted.
